## 1. 定位与范围

**定位**：火瞳是冯校长火锅浙江总代的连锁 AI 运营中台，以视觉与经营数据双引擎服务两家自营店验证，之后沉淀为区域门店标准。

**一句话价值**：摄像头看见后厨与前厅异常，数据引擎辅助算清损耗和订货，店长在同一工作台完成确认与复盘。

### 1.1 三阶段路线

| 阶段 | 目标 | 门槛 |
|---|---|---|
| 当前：两店验证 | 椒江、玉环的真实数据和流程跑通 | 原始 POS、人工核验、店长确认、前后对照 |
| 区域标准化 | 形成浙江新店部署与运营标准 | 两店可复用、数据一致、部署可控 |
| 对外输出 | 向体系内及外部连锁复制 | 真实 ROI、稳定交付与合规定价 |

### 1.2 明确边界

- 火瞳连接 POS、ERP、库存、采购和会员系统，**不取代**它们。
- 火瞳可给出预警、损耗估算和订货建议；正式采购、库存扣减和关键食安处置必须由授权人员确认。
- 当前优先两家自营店，不以外部收费、客户数量或市场规模作为当前阶段验收指标。

## 2. 用户与工作闭环

| 角色 | 主要问题 | 火瞳交付 |
|---|---|---|
| 店长 | 今天哪些事情必须处理 | 高优先级待办、原因、动作、结果 |
| 后厨负责人 | 备货、报损、SOP 如何纠偏 | 废料事件、品质/SOP 提醒、人工确认 |
| 采购 | 该买多少、供应商是否可靠 | 预测范围、库存风险、采购建议（人工确认） |
| 区域运营/总代 | 两店及后续门店哪里异常 | 多店对比、周复盘、标准执行情况 |
| 老板 | 是否改善利润、是否值得复制 | 损耗、缺货、周转、ROI 与复制门槛 |

闭环统一为：**采集事件 → 识别/计算 → 告警或建议 → 人工确认 → 处理结果 → 周度复盘 → 规则改进**。

## 4. 数据与证据规范

### 4.1 数据源分层

| 等级 | 定义 | 可以支持的结论 |
|---|---|---|
| D1 设计 | PRD、架构、原型 | 计划与假设 |
| D2 代码 | 模块、接口、页面可运行 | 具备代码基础 |
| D3 模拟 | 演示 CSV、Mock 传感器 | 开发验证 |
| D4 真实门店 | 原始导出、人工核验、负责人确认 | 试点通过、ROI、复制标准 |

### 4.2 POS 与回测硬规则

- 真实 POS CSV 必须保留 `business_date`、SKU、数量、价格及来源门店。
- 导入前运行 `scripts/validate_pos_history.py`，输出文件 SHA-256、日期覆盖、缺失日和重复记录。
- 回测使用 `scripts/backtest_real_pos_l1.py`；默认要求至少 90 个经营日，报告必须附源文件指纹。
- L1 MAPE ≤45% 才可进入“可用”评估；45%-55% 只能带校准试运行；>55% 不进入订货建议阶段。

## 5. 试点实施与 Go/No-Go

### M0：Sprint 0（真实数据验证）

1. 椒江店导出原始 POS 逐 SKU 历史数据，形成来源台账。
2. 执行字段、日期、重复记录和覆盖天数校验。
3. 完成真实 L1 回测；后续模型须明确标注所用数据和版本。
4. 完成店长、后厨负责人、采购三类内部访谈并形成纪要。

**M0 Go**：POS 证据通过 + 回测达到门槛 + 访谈确认数据与流程可用。

### M1：两店运行验证

- 椒江店：废料、桌态、日报、POS 与人工确认闭环。
- 玉环店：复用配置，验证跨店数据口径和区域看板。
- 每周只调整一个规则；记录告警有效率、处理率、损耗金额和店长采纳率。

### M3：是否复制

仅当数据链路稳定、人工核验可信、经营指标改善且部署可复用时，才发布浙江总代门店标准；否则继续优化，不对外承诺 ROI。

## 6. 非功能与治理

- 边缘优先：视频不上传云端；断网本地记录、联网同步。
- 门店隔离：数据与权限按门店、区域、总部角色控制。
- 审计：关键建议、确认、修改和结果可追溯。
- 食安：高风险事件必须保留人工处置链路。
- 可靠性：设备、传感器、数据源离线必须产生明确告警，不可静默降级。
