# 火瞳项目 — DoR / DoD 正式标准定义

> **版本**: v1.0
> **生效日期**: 2026-08-01
> **适用范围**: 火瞳项目全部开发活动 (feature/d1-expo-sprint 分支)
> **制定依据**: Scrum + Design-First 混合开发模式

---

## 1. 背景与目的

### 1.1 为什么需要 DoR / DoD

在之前的开发过程中，我们发现以下问题：

| 问题 | 影响 | 示例 |
|------|------|------|
| 任务直接从 PRD 跳到代码实现 | 缺少设计环节，导致返工 | D1-S01 先写代码后补设计文档 |
| Task 完成标准不明确 | "做完了"定义模糊，质量参差 | 部分API无测试就标记Done |
| Sprint 过程资产缺失 | 无法追溯决策过程 | 无Backlog/回顾文档 |

### 1.2 本文档目标

1. **明确准入标准**: 什么条件下 Task 可以进入 Sprint
2. **统一完成标准**: 什么条件下 Task 可以标记为 Done
3. **提升可追溯性**: 每个 Task 都有清晰的设计→代码→测试链路
4. **保证质量底线**: 防止"半成品"进入下一环节

---

## 2. Definition of Ready (DoR) — 任务准入标准

### 2.1 核心原则

> **"没有设计的代码不值得写，没有追溯的需求不值得做"**

### 2.2 五项检查标准 (DR-1 ~ DR-5)

#### DR-1: ✅ 有对应的设计文档 (Design-First)

**要求**: Task 必须有对应的设计文档作为输入

**验证清单**:
- [ ] 设计文档存在于 `docs/04-技术设计/` 目录下
- [ ] 或 PRD 中有明确的功能需求描述（EARS格式）
- [ ] 文档包含：数据模型/API契约/状态机/业务规则（至少3项）
- [ ] 文档最后修改时间 ≥ Task 创建时间

**例外情况** (需PMO批准):
- 纯Bug修复（有Issue即可）
- 基础设施/工具脚本（有简要说明即可）

**示例**:
```
✅ 合格: D1-S01 有 docs/04-技术设计/D1-S01_货品主数据详细设计_v1.0.md
❌ 不合格: 直接说"实现用户登录"，无设计文档
```

---

#### DR-2: ✅ 需求来源可追溯 (Traceability)

**要求**: Task 必须关联到 PRD 功能点或用户故事

**验证清单**:
- [ ] Task 描述包含 "对应PRD: Lxxx" 或 "Epic: xxx"
- [ ] 或关联到 User Story ID (如 US-D1-S01-001)
- [ ] 需求描述包含验收标准 (Acceptance Criteria)
- [ ] 利益相关方明确（谁使用、谁受益）

**追溯格式**:
```markdown
## 需求追溯
- **PRD来源**: 火瞳_融合PRD_v5.3_主线基线.md → L386 EARS需求
- **Epic**: D1 冻品供应链 → S01 货品主数据管理
- **User Story**: 作为曹总，我希望统一SKU编码体系，以便避免采购混乱
- **验收标准**:
  1. 支持货品CRUD操作
  2. SKU编码唯一且自动大写
  3. 锁定后关键字段不可修改
```

---

#### DR-3: ✅ 估算合理且有边界 (Bounded Scope)

**要求**: Task 粒度适中，工作量可预估

**验证清单**:
- [ ] 预估工时 ≤ 1天 (8小时)
- [ ] 如超过1天，必须拆分为子Task
- [ ] 验收标准明确（可测试的、具体的）
- [ ] 边界清晰（做什么、不做什么）

**粒度指导**:

| Task 规模 | 示例 | 处理方式 |
|-----------|------|----------|
| **合适** (2-8h) | "实现货品列表API + 分页" | ✅ 可直接开始 |
| **过大** (>8h) | "实现完整的供应链模块" | ❌ 必须拆分 |
| **过小** (<30min) | "修复一个typo" | ⚠️ 合并为批量Task |

**拆分示例**:
```
❌ 过大: "D1-S02 收货质检功能"
   ↓ 拆分为
✅ 合理:
  - D1-S02-01: 设计 ReceivingRecord 数据模型 (2h)
  - D1-S02-02: 实现 VLM 视觉质检接口 (4h)
  - D1-S02-03: 实现潘厨审批工作流 (3h)
  - D1-S02-04: 新增 receiving_api.py (2h)
  - D1-S02-05: 收货质检前端页面 (3h)
```

---

#### DR-4: ✅ 技术方案可行 (No Blockers)

**要求**: 无技术阻塞，依赖项已识别

**验证清单**:
- [ ] 前置依赖 Task 已完成或标注为"并行可开始"
- [ ] 技术方案经过简单评估（可行性确认）
- [ ] 所需依赖库/服务可用（或Mock方案已准备）
- [ ] 风险已识别并有缓解措施

**依赖声明格式**:
```markdown
## 前置依赖
- [x] D1-S01 货品主数据 (SKU基础数据) ✅ 已完成
- [ ] VLM Bridge 部署到 Jetson 🔲 待部署
  - 缓解方案: 先用 Mock 数据跑通流程

## 技术风险
- **风险**: Jetson ARM64 架构可能缺少某些Python包
- **缓解**: 提前在 Jetson 上验证依赖安装
- **影响**: 中等 (可降级为CPU推理)
```

---

#### DR-5: ✅ 代码规范明确 (Code Standards)

**要求**: 遵循项目编码规范

**验证清单**:
- [ ] 已阅读 `docs/04-开发基线/PROJECT_BASELINE_V5_2.md`
- [ ] 了解 Python 版本要求 (3.8+ 兼容)
- [ ] 了解类型注解规范 (Optional[T] 非 T | None)
- [ ] 了解命名约定 (snake_case / PascalCase / UPPER_CASE)
- [ ] 了解 Git 提交规范 (Conventional Commits)

**快速参考**:

| 规范项 | 要求 |
|--------|------|
| Python版本 | 3.8+ 兼容 (Jetson 为 3.9.5) |
| 类型注解 | `Optional[int]` ✅ / `int \| None` ❌ |
| 字符串引号 | ASCII 直引号 `"` / `'` |
| 命名风格 | 函数/变量: snake_case, 类: PascalCase, 常量: UPPER_CASE |
| Commit格式 | `type(scope): subject` (见下方) |
| 文件头注释 | 模块说明 + 作者 + 日期 |

**Commit Message 规范**:
```
<type>(<scope>): <subject>

<body (可选)>

<footer (可选)>
```

**Type 枚举**:
- `feat`: 新功能
- `fix`: Bug修复
- `docs`: 文档变更
- `refactor`: 重构 (不改变行为)
- `test`: 测试相关
- `chore`: 构建/工具/辅助变更
- `perf`: 性能优化

**示例**:
```
feat(supply-chain): D1-S01 货品主数据管理模块

实现完整的货品主数据CRUD功能(Expo Demo可用):
  - ProductMaster 数据模型 (8个Pydantic模型)
  - SupplyChainManager CRUD方法 (13个@classmethod)
  - product_master_api.py (13个RESTful端点)
  - products.html + product-master.js (前端页面)

Closes #202
```

## 3. Definition of Done (DoD) — 任务完成标准

### 3.1 核心原则

> **"'做完了'意味着可以交付给用户使用，而非'代码写完了'"**

### 3.2 五项检查标准 (DD-1 ~ DD-5)

#### DD-1: ✅ 代码已完成并提交 (Committed Code)

**要求**: 代码已 commit 到 feature 分支并通过基本验证

**验证清单**:
- [ ] 所有新增/修改文件已 `git add`
- [ ] Commit message 符合规范 (Conventional Commits)
- [ ] 代码可在本地正常运行 (`python3 xxx.py` 无报错)
- [ ] 无 `TODO` / `FIXME` / `HACK` 注释残留（或有明确Issue跟踪）
- [ ] 无 `print` 调试语句残留
- [ ] 无硬编码的敏感信息（密码/Token/IP）

**提交前自查命令**:
```bash
# 1. 语法检查
python3 -m py_compile <file>.py

# 2. 导入检查
python3 -c "from hotpot_platform.cloud.supply_chain.models import *"

# 3. 格式检查 (如有配置 black/flake8)
# black --check <file>.py

# 4. Git状态检查
git status --short  # 应仅显示目标文件
```

---

#### DD-2: ✅ 测试通过 (Tests Passing)

**要求**: 核心功能有对应测试用例且通过

**验证清单**:
- [ ] 每个公开 API/函数至少有 1 个正常流程测试
- [ ] 关键业务逻辑有边界条件测试
- [ ] 错误处理路径有异常流程测试
- [ ] 测试结果记录在案（pytest输出或手动测试记录）

**最低测试覆盖要求**:

| 功能类型 | 最低测试数 | 测试类型 |
|----------|-----------|----------|
| CRUD API | ≥5 (增删改查+列表) | 手动/API测试 |
| 业务规则 | ≥3 (正常+异常+边界) | 单元测试 |
| 状态机 | ≥N×2 (N=状态数, 每状态2转换) | 单元测试 |
| 前端页面 | ≥3 (加载+核心操作+响应式) | 手动测试 |

**测试记录模板**:
```markdown
### 测试结果 (YYYY-MM-DD)

| 用例编号 | 测试项 | 操作 | 预期结果 | 实际结果 | 状态 |
|----------|--------|------|----------|----------|------|
| T01 | 登录获取Session | POST /auth/login | 返回session_id | 返回xxx | ✅ Pass |
| T02 | 统计概览 | GET /products/stats | 返回统计数据 | 返回24货品 | ✅ Pass |

**通过率**: X/Y (Z%)
**环境**: Python 3.9.5 / macOS / Edge UI :9080
```

---

#### DD-3: ✅ 无已知阻塞性Bug (No Blocking Bugs)

**要求**: P0/P1 级 Bug 为 0

**验证清单**:
- [ ] P0 (功能不可用): 0 个
- [ ] P1 (主要功能受损): 0 个
- [ ] P2 (次要功能受限): 可接受，但必须记录在 Known Issues
- [ ] P3 (优化建议): 不阻塞 Done

**Bug分级标准**:

| 级别 | 定义 | 示例 | 是否阻塞Done |
|------|------|------|--------------|
| **P0** | 功能完全不可用 | API返回500，无法启动 | 🔴 阻塞 |
| **P1** | 主要功能受损 | 核心CRUD无法完成 | 🔴 阻塞 |
| **P2** | 次要功能受限 | 变更申请API报错 | 🟡 记录后可Done |
| **P3** | 体验优化建议 | UI样式微调 | 🟢 不阻塞 |

**Known Issues 格式**:
```markdown
### Known Issues (非阻塞)

| Issue ID | 描述 | 影响范围 | 优先级 | 计划修复 |
|----------|------|----------|--------|----------|
| KI-001 | 变更申请model校验错误 | POST /products/{sku}/change | P2 | S02前修复 |
| KI-002 | 路由顺序问题 | GET /products/changes | P2 | 下个迭代 |
```

---

#### DD-4: ✅ 文档同步更新 (Docs Synced)

**要求**: 如有设计变更，文档已同步更新

**验证清单**:
- [ ] 设计文档最后修改时间 ≥ 代码提交时间
- [ ] 或有明确的"文档待更新"备注 + 对应Task
- [ ] README/CHANGELOG (如有) 已更新
- [ ] API文档 (如有) 与代码一致

**文档同步检查清单**:

| 变更类型 | 需更新的文档 | 更新内容 |
|----------|-------------|----------|
| 新增API端点 | 详细设计文档 | API契约章节 |
| 数据模型变更 | 详细设计文档 + 数据字典 | 字段说明 |
| 状态机调整 | 详细设计文档 | 状态机图 + 转换规则 |
| 前端页面新增 | 详细设计文档 | 页面结构 + 交互说明 |
| Bug修复 | Known Issues | 新增或关闭Issue |

---

#### DD-5: ✅ Code Review 通过 (Code Quality)

**要求**: 代码符合项目规范（自查或同行评审）

**验证清单** (自查模式):

**命名与风格**:
- [ ] 变量/函数命名符合 snake_case / PascalCase 规范
- [ ] 无过长的函数 (>50行考虑拆分)
- [ ] 无过深的嵌套 (>4层考虑重构)
- [ ] 有必要的行内注释解释复杂逻辑

**类型安全**:
- [ ] 公开函数有完整的类型注解
- [ ] Pydantic 模型字段有 Field 约束
- [ ] 无 `Any` 类型滥用 (必须有明确理由)

**错误处理**:
- [ ] 外部调用有 try-except 包裹
- [ ] 异常信息有意义（不含敏感数据）
- [ ] HTTP API 有正确的状态码返回

**性能考量**:
- [ ] 无明显的 N+1 查询问题
- [ ] 大数据量场景有分页/限制
- [ ] 无不必要的循环内IO操作

**安全检查**:
- [ ] 无 SQL注入风险 (当前用JSON存储，无需担心)
- [ ] 无 XSS 风险 (FastAPI自动转义)
- [ ] 敏感信息不硬编码 (密码/Token用环境变量)

## 4. 与 Design-First 原则的映射

### 4.1 三原则 ↔ DoR/DoD 对应关系

我们确立的开发模式三原则：

| 原则 | 含义 | DoR 映射 | DoD 映射 |
|------|------|----------|----------|
| **原则1**: 代码基于产品设计/架构设计开发 | Design-First | DR-1 (有设计文档) | DD-4 (文档同步) |
| **原则2**: 当前代码必须先和设计对齐再继续开发 | Design-Code Alignment | DR-2 (需求可追溯) | DD-5 (Code Review) |
| **原则3**: 开发中任何修改 → 先调整设计文档 → 再修改代码 | Change Control | DR-5 (规范明确) | DD-1 (代码提交) |

### 4.2 违规处理

如果发现 Task 未满足 DoR 就开始开发：

| 违规等级 | 情况 | 处理措施 |
|----------|------|----------|
| **轻微** | 有PRD描述但无独立设计文档 | 补充简要设计（≥200字）后再继续 |
| **中等** | 既无设计也无PRD直接引用 | 立即暂停，补充设计文档 |
| **严重** | 跳过设计直接写代码且已完成 | ① 补齐设计文档 ② 写复盘总结 ③ Sprint回顾时检讨 |

## 5. 实施指南

### 5.1 Task 创建模板

新建 Task 时，请使用以下模板：

```markdown
## {Task ID}: {Task 标题}

### 需求追溯
- **PRD来源**: {文档名} → L{行号}
- **Epic**: {所属Epic}
- **User Story**: As a {角色}, I want to {功能}, So that {价值}

### DoR 检查
- [ ] DR-1: 设计文档 → {文档路径}
- [ ] DR-2: 需求追溯 → {Epic/Story ID}
- [ ] DR-3: 工作量估算 → {X}h
- [ ] DR-4: 前置依赖 → {列表 or "无"}
- [ ] DR-5: 代码规范 → 已阅读 PROJECT_BASELINE

### 验收标准 (Acceptance Criteria)
1. AC-1: {具体、可测试的标准}
2. AC-2: ...
3. AC-3: ...

### DoD 检查 (完成后填写)
- [ ] DD-1: 代码已提交 → {Commit ID}
- [ ] DD-2: 测试通过 → {X/Y 通过率}
- [ ] DD-3: 无阻塞性Bug → P0={0} P1={0}
- [ ] DD-4: 文档已同步 → {是/否 + 说明}
- [ ] DD-5: 代码质量OK → {自查/Review结果}
```

### 5.2 Sprint Planning 检查清单

每周一 Sprint Planning 时：

```
□ 回顾上周 Done 的 Task DoD 完成情况
□ 检查本周 To Do 的 Task DoR 准备情况
□ 识别跨 Task 依赖关系
□ 评估团队容量 (可用工时)
□ 确认优先级排序 (P0 > P1 > P2)
□ 更新 Sprint Backlog 看板
```

### 5.3 Sprint Review 检查清单

每周五 Sprint Review 时：

```
□ Demo 本周完成的 Task
□ 统计 DoD 达标率 (满足5项的Task占比)
□ 复盘未达标项及原因
□ 更新 Known Issues 清单
□ 识别下周风险和阻塞
□ 更新 Sprint Backlog 文档
```
