### 2.1 Sprint 0: 前置验证 ✅

**目标**: 验证双引擎（视觉AI + 数据引擎）技术可行性

**时间**: 2026-06-15 ~ 2026-06-30

#### 成果

| 验证项 | 结果 | 详情 |
|--------|------|------|
| 椒江店数据回测 | ✅ Pass | Go模型 MAPE 10.6%（目标<15%） |
| 玉环店损耗闭环 | ✅ Pass | 7/7 测试用例全部通过 |
| Jetson部署验证 | ✅ Pass | ARM64 + Ubuntu 20.04 环境就绪 |
| 海康NVR接入 | ⚠️ 部分 | HTTP抓拍✅ / RTSP❌(554关闭) |

#### 关键决策

| 决策 | 内容 | 影响 |
|------|------|------|
| 采用Go模型 | 而非LSTM/Prophet | 更轻量，适合Edge场景 |
| HTTP抓拍替代RTSP | 绕过NVR端口限制 | 延迟~170ms，可接受 |
| 确认技术栈 | Python 3.9 + PyTorch + OpenCV | 后续开发基准确定 |

#### 经验教训

**做得好的**:
1. ✅ 先做技术验证再大规模开发，避免选型错误
2. ✅ 在真实门店环境（椒江店Jetson）验证，而非仅本地Mock

**需改进的**:
1. ❌ NVR RTSP端口问题发现较晚，应提前做网络扫描
2. ❌ 缺少性能基线数据（推理耗时/内存占用）

**改进措施**:
- 新环境接入前先做完整的端口/服务扫描
- 建立性能基准文档（记录各模型的推理指标）

### 2.3 D2: 岗位AI助理冲刺 ✅ (框架)

**目标**: 实现 SOP 合规引擎 + 知识检索 + Agent 框架

**时间**: 2026年7月第二周

#### 成果

| 模块 | 功能 | 完成度 |
|------|------|--------|
| SOP 引擎 | 规则定义 + 执行检测 + 违规记录 | 80% |
| 知识检索 | RAG 接口 + FAQ 问答 | 70% (缺向量库) |
| Agent 框架 | Agent基类 + 工具调用 + 多轮对话 | 75% |
| 数字座舱 | Dashboard 页面 + KPI 卡片 + 图表组件 | 70% |

#### 关键架构决策

```
Agent 架构选择:
  方案A: 单一大模型 (GPT-4 → 全能)
  方案B: 专业小模型组合 (多Agent协作) ✅ 选择

原因:
  - Edge 场景资源有限 (Jetson 4GB RAM)
  - 不同任务需要不同专长 (质检 vs 问答 vs 推荐)
  - 可独立升级单个Agent不影响其他
```

#### 问题与挑战

| 问题 | 影响 | 解决方案 |
|------|------|----------|
| LLM选择未定 | Agent能力边界不清 | 先定义接口，支持多后端切换 |
| 知识库内容空缺 | RAG检索无数据 | 准备导入产品手册和操作指南 |
| SOP规则库为空 | 合规检查无规则可执行 | 计划填充20+火锅行业SOP |

#### 经验教训

**做得好的**:
1. ✅ Agent 设计采用插件化架构，易于扩展
2. ✅ SOP 引擎与业务解耦，规则可配置

**需改进的**:
1. ❌ 过于注重框架，缺少实际业务场景对接
2. ❌ 缺少端到端的用户交互演示

**改进措施**:
- D2深化阶段聚焦"收货质检"这一具体场景
- 制作 Demo 视频展示 Agent 对话流程

### 2.6 Edge UI v1.1 重构冲刺 ✅

**目标**: 从 http.server 迁移到 FastAPI + 增加 L2 PIN 认证

**时间**: 2026年7月最后一周

#### 成果

| 指标 | 重构前 | 重构后 |
|------|--------|--------|
| Web框架 | http.server (标准库) | FastAPI (第三方) |
| API数量 | 5个手动路由 | 9个模块化路由 |
| 认证机制 | 无 | L2 PIN Session |
| 自动文档 | 无 | Swagger UI + ReDoc |
| 代码行数 | ~1,500 | ~11,000 (+9,387) |
| 代码质量 | 过程式 | 面向对象 + 类型注解 |

#### 关键技术决策

```
为什么选择 FastAPI?
  ✅ 自动生成 OpenAPI 文档
  ✅ Pydantic 原生集成 (类型安全)
  ✅ 异步支持 (async/await)
  ✅ 依赖注入 (Depends 模式用于认证)
  ✅ 性能优秀 (Starlette 底层)
  ✅ 社区活跃 (适合长期维护)
```

#### 问题与挑战

| 问题 | 影响 | 解决方案 |
|------|------|----------|
| 旧路由兼容性 | 前端页面404 | 统一路由前缀 `/api/v1/` |
| Session存储 | 多实例不共享 | 文件Session (单门店够用) |
| PIN码硬编码 | 安全风险 | 后续迁移到环境变量 |

#### 经验教训

**做得好的**:
1. ✅ 保持向后兼容，前端页面无需大改
2. ✅ 认证中间件采用 Depends 注入，优雅且易扩展

**需改进的**:
1. ❌ 重构过程中缺少自动化回归测试
2. ❌ PIN码应从配置文件读取，非硬编码

**改进措施**:
- 重构前先写测试套件（D3的经验）
- 敏感信息统一走环境变量或配置文件
