## 二、P0 问题清单（阻塞级·必须展会前解决）

### P0-1 【架构映射】K系列功能编号PRD与详细架构§8严重不一致
- **问题**：PRD §3中K01=废料检测/K02=废料计数/K03=日报/K04=桌态/K05=空桌提醒；但详细架构§8中K01=桌态识别/K02=顾客人数/K03=剩余率/K04=翻台率/K05=加汤提醒。两份核心文档对同一编号的定义完全不同。
- **影响**：开发者、测试者无法确认哪个文档是准确的——PRD说是废料，架构说是桌态。这是阻塞级混淆。
- **建议**：立即以PRD为唯一源，全量修正详细架构§8的K系列编号。PRD是"编号唯一源"，但详细架构未执行此原则。

### P0-2 【数据流闭环】Agent Gateway高风险操作边界未实际运行验证
- **问题**：PRD §1.10和总体架构明确AI不自动创建PO、需人工审批。Agent Gateway的ActionType(22种)+RiskLevel(5级)+PermissionMatrix已在代码中实现，但实际门店端到端测试中尚未执行过"PO创建→Gateway拦截→人工审批→审计记录"完整链路。
- **影响**：展会演示时，如果投资人现场要求演示"AI建议→人工审批→不下单"的合规闭环，可能无法流畅演示。
- **建议**：D3集成测试中必须增加一条TC：模拟AI试图自动创建PO→Gateway拦截→审批流程→审计日志写入→通过验证。

### P0-3 【安全设计】JWT默认密钥为明文"hotpot-dev-secret-change-in-prod"
- **问题**：详细架构§6.1环境变量中`HOTPOT_JWT_SECRET`默认值为文字`hotpot-dev-secret-change-in-prod`。虽然文档标注了"生产必须修改"，但代码中如果未做"生产环境强制缺少即拒绝启动"的硬检查，存在安全隐患。
- **影响**：如果生产部署忘记修改，所有JWT Token可被伪造。
- **建议**：①代码层增加`if HOTPOT_ENV != 'dev' and JWT_SECRET == default: raise FatalError` ②展会部署前执行安全配置检查清单。

### P0-4 【展会匹配】Agent自然语言入口（NL Entry）不在D1-D4冲刺范围内
- **问题**：PRD §1.8.4明确标注"G4: Agent自然语言入口缺失"为P0差距。但NL入口的实现计划被放在"展会后2周"（§1.10.4 NL-P0）。这意味着10月展会上，A01-A05助理只能通过API调用或Demo界面展示，没有"一句话交互"的自然体验。
- **影响**：投资人/参观者通常会问"我能不能直接和它说话"，如果只能点击按钮/API调用，产品感知度大幅下降。
- **建议**：①至少实现1个角色的NL Demo（如店长助理文本聊天），接入轻量LLM+意图路由 ②录制带有NL交互的视频作为兜底。

### P0-5 【数据流】云端Event Hub主写模式与Edge直写的旧模式并存
- **问题**：详细架构§E.1明确Event Hub应为"Hub主写模式"，但当前Edge仍为直写旧模式（标注"⚠️ 待改造 P0阻塞"）。总体架构v2.1已在修订中统一事件路径为`/api/v1/events(Hub主写模式)`，但实际代码未迁移。
- **影响**：边缘-云端数据流架构约定与实现不符，数据一致性无法保证。
- **建议**：D3集成测试前必须完成Hub主写模式切换，旧Edge直写端点添加@deprecated标记。

## 三、P1 问题清单（重要级·展会前优先处理）

### P1-1 【架构自洽】三份文档端口定义不一致
- **问题**：
  - 总体架构v2.1: Event Hub端口=8098
  - 详细架构v1.6: Event Hub端口=8088（多处）
  - PRD §1.11.3: EVENT_HUB_PORT=8098
  - 详细架构§E.1端口表：Edge Agent API=8088, Platform Dashboard=8098
- **影响**：部署配置混乱，Docker Compose和边缘设备.env文件无法对齐。
- **建议**：统一Event Hub主端口，建议以总体架构的8098为准。三文档一致性扫描必须纳入CI检查。

### P1-2 【架构映射】详细架构§8的129项映射仅29.5%有API端点
- **问题**：详细架构§8的映射统计显示：129项功能中仅38项有API端点（29.5%），仅52项有DB表映射（40.3%），仅24项有代码位置（18.6%）。82项（63.6%）标注为⬜未来规划。
- **影响**：展会Demo需要展示的核心功能（S01-S03、A01-A03）虽有代码基础，但API映射表中均为⬜或📐。
- **建议**：展会前为D1-D4的10个核心功能补齐API端点和代码位置映射。详细架构§8应该成为"活的追踪表"而非一次性文档。

### P1-3 【技术债务】多租户tenant_id字段在所有核心表中缺失
- **问题**：PRD §1.11定义了完整的多租户对象层级（租户→品牌→区域→门店→设备）和16个业务事件必携字段。详细架构的19张DDL表中（events/sales_daily/inventory_ledger等）均**无tenant_id字段**。虽然有org_structure表做组织架构，但数据表本身无租户隔离。
- **影响**：当前只能单租户运行。加盟模式一旦开始，所有查询必须加入WHERE tenant_id，这是大规模重构。
- **建议**：①展会后首轮（2026Q4）在所有核心表追加tenant_id字段+索引 ②搭建数据库中间件实现自动注入 ③迁移脚本预留回滚方案。

### P1-4 【过度设计】会员营销模块（FH01-FH04）定义过于超前
- **问题**：详细架构§1.9定义了完整的人脸识别会员系统（FaceNet+Faiss+差分隐私）、积分引擎（DSL规则）、营销引擎、会员画像。但当前处于两店验证阶段，人脸识别涉及个人信息保护法合规（需征得同意），且RFID/电子秤等基础设施尚未部署。
- **影响**：这部分设计占用文档和评审精力，却不可能在展会上演示。
- **建议**：将FH01-FH04明确标记为"Phase 2架构预留"，在详细架构中减少到仅保留接口定义，移除完整类设计。

### P1-5 【断网机制】降级触发条件缺乏量化阈值
- **问题**：总体架构§5.4描述了离线模式→24h告警→恢复同步的流程，详细架构§4.5定义了重试策略。但缺乏关键量化阈值：
  - L1→L2→L3→L4降级触发（什么条件下SARIMA降级到移动平均？）
  - 断网24h后本地存储满的处理（"丢弃最旧条目"可能丢失关键食安数据）
  - 恢复后数据同步的一致性校验（去重仅靠event_id，但离线产生的event_id和云端可能冲突）
- **建议**：①明确预测降级的触发条件（如MAPE连续2天>30%触发降级） ②断网超24h触发"优先保留critical级别事件"策略 ③恢复同步增加数据校验sum。

### P1-6 【安全设计】设备认证双轨制（PIN+API Key+JWT）过渡期风险
- **问题**：详细架构§E.1标注"认证方式混用(PIN/JWT/API Key)"为TD-4。PRD §1.11要求使用"可轮换凭证和首次注册令牌"。但实际设备注册使用API Key体系，用户认证是JWT。PIN体系在"过渡"中但仍有残余。
- **建议**：展会前完成PIN→JWT全量迁移（Phase3报告已完成），移除所有PIN认证代码路径。设备端统一使用可轮换API Key。

## 四、P2 问题清单（改善级·展会后处理）

### P2-1 【技术债务】测试文件仍有25+处硬编码store_id和demo路径
- **问题**：PRD §1.11.7整改清单明确指出"测试文件仍有25+处硬编码（tests/test_*.py, scripts/train_table_classifier.py）"和"pipeline_config_jiaojiang.yml仍引用demo图片"。这是通用化改造的代码层欠账。
- **建议**：展会后首轮技术债清偿Sprint中，批量替换测试文件中的store_xxx为参数化fixture。

### P2-2 【过度设计】详细架构§1.6-1.9的接口定义过于"代码即文档"
- **问题**：SOP合规引擎、知识库检索、仓库IoT、会员营销四个模块的接口定义采用了完整Python代码写法（类定义+参数+返回值结构），导致详细架构膨胀至3,499行。这些细节更适合放在独立的模块设计文档中。
- **建议**：将详细架构中的完整Python类定义迁移到独立的模块设计文档（如`SOP引擎详细设计v1.0.md`），在详细架构中保留接口摘要+文档引用。

### P2-3 【架构自洽】总体架构v2.1的代码行统计口径与详细架构v1.6不一致
- **问题**：总体架构v2.1标注"代码基线：~43,569行/262 py文件/45测试文件"，详细架构v1.6标注"代码基线：~43,569行/375 py文件/68测试文件"。两处均声明"采用更精确的排除规则"，但用户不知道哪个是真实数字。
- **建议**：统一统计口径。以详细架构v1.6的375 py/68测试为准（排除__pycache__/venv）。总体架构中注明"详见详细架构v1.6"。

### P2-4 【展会匹配】D4 Demo数据策略中"模拟数据兜底"占比过高
- **问题**：§4A.8 Demo数据策略中标注"冻品供应链: D3模拟→D4待验证"、"岗位AI助理: D3模拟→D4待验证"、"全场景座舱: D3模拟→D4待验证"。投资人可能会质疑"这是真实运行还是录屏"。
- **建议**：展会前务必将"真实数据为主"的D4场景扩充至3个以上。至少确保废料检测（已有录制）+ 损耗闭环（玉环7/7）+ 预测（MAPE 10.6%）3个场景有真实数据支撑。

### P2-5 【架构演化】ADR-007/008/009/010长期处于"待确认"状态
- **问题**：总体架构§8的16项ADR中，4项（多租户tenant_id/Agent框架LangGraph/消息总线Redis PubSub/云端阿里云）自v1.0起一直标记为"🔄待确认/待实现"。这些决策影响核心架构方向。
- **建议**：展会后对4项ADR做正式决策评审。尤其是Agent框架选型和消息总线选型，这决定P2阶段的架构形态。

### P2-6 【文档治理】PRD v5.3o长达3,438行，全文无版本化功能变更追踪
- **问题**：PRD从v5.3a到v5.3o的每次变更都在头部的版本历史中列出，但正文中无法区分"新增内容"和"已有内容"。新加入团队的开发者很难快速定位"展会的P0功能在哪"。
- **建议**：在PRD中为展会M3相关的功能ID标注🎯M3标记。或拆分"展会版本"和"完整版本"两份文档。

### 5.2 4+1视图自洽性（评分：78/100）

**已自洽**：
- 逻辑→开发→运行→物理→场景五视图在总体架构中均有对应章节
- 跨视图一致性矩阵（§6）建立了逻辑-代码-进程-硬件四维映射
- 场景视图（§5）含5个核心场景的完整时序图

**不自洽点**：
- 端口不一致（总体架构8098 vs 详细架构8088）
- 代码行数不一致（262py vs 375py）
- 运行视图的进程端口与详细架构§E.1端口表不完全对应
- 逻辑视图中Edge UI(9100)与详细架构E.1中Edge Agent API(8088)/Edge UI(9080)编号冲突

### 5.3 边缘-云端数据流设计（评分：75/100）

**设计优势**：
- "视频不上云、仅传结构化事件"的架构原则在不同层级文档中一致
- 16个业务事件必携字段定义完整（PRD §1.11.4）
- 单店→区域→总部三级数据管道设计清晰（PRD §3C/3B）
- 事件驱动协议（详细架构§4）覆盖视觉/IoT/POS/系统四类事件

**设计不足**：
- MQTT管道标注"🔄待建"（总体架构ADR-016），但实际边缘端已使用HTTP上报，MQTT定位模糊
- Real/Mock/Simulated数据的运行时混合策略不清晰——PRD §1.11.6定义了Demo/Mock隔离规范，但边缘端如何区分"真实VLM推理"和"Mock桩"缺乏运行时检测机制
- 云端Hub主写 vs Edge直写的迁移无时间线

### 5.4 断网/降级/恢复机制（评分：70/100）

**设计优势**：
- 总体架构§5.4详细描述了4种断网模式（门店断/区域断/全断）和恢复同步流程
- store_forward.py + SQLite离线队列设计完整（详细架构§4.5）
- 24h本地存活目标明确，硬件双链路（4G+宽带）支持到位
- 预测四级降级链（L1规则→L2 SARIMA→L3 LGB→L4 LLM）设计合理

**设计不足**：
- 缺乏降级触发条件的量化：什么条件下触发L2→L1？SARIMA模型加载失败？预测结果连续异常？文档未定义
- 离线队列的"丢弃最旧条目"策略对食安场景（温度超限告警）不够安全
- 断网恢复后的"补推送遗漏告警（去重）"未定义去重算法

### 5.5 安全设计（评分：68/100）

**已完成**：
- JWT认证体系 + RBAC 12角色矩阵（详细架构§3.2）
- API Key设备认证 + JWT用户认证双轨制
- 密钥管理策略（Vault/环境变量/90天轮换）
- 审计日志表（audit_logs）DDL完整
- "视频不上云"的架构级隐私保护
- 会员人脸特征SHA-256 Hash上传而非原始特征

**待补强**：
- 多租户tenant_id未在所有核心表中实现
- JWT_SECRET默认值为明文硬编码字符串
- 无API限流（详细架构错误码42901定义了但无中间件实现）
- 无TLS版本强制要求（PRD说TLS 1.2+，总体架构说TLS 1.3）
- 无SQL注入/CSRF/XSS防护描述

### 5.6 技术债务与过度设计（评分：65/100）

**已识别的技术债务（总体架构TD-01至TD-10 + 详细架构TD-1至TD-5 = 15项）**：

## 七、结论

**整体判断**：feature/arch-design分支的架构设计**质量较高、方法规范**。PRD v5.3o的129项功能完整、4+1视图方法正确运用、断网/降级机制设计详细、展会冲刺计划合理。

**三个核心矛盾**：
1. **文档-代码鸿沟**：通用化改造6/6文档完成 vs 1/6代码完成，这是从"设计好"到"运行好"的最大障碍
2. **编号混乱**：PRD和详细架构的K系列功能编号完全不同，这是阻塞级问题
3. **超前设计**：在2店验证阶段设计了完整的加盟连锁、会员营销、Agent热插拔——应聚焦P0，展会后渐进式扩展

**一句话建议**：**守住展会5场景的P0质量，修好编号和端口的不一致，展会后用3个月清偿技术债务（tenant_id、测试硬编码、Hub主写迁移），然后才启动P2的连锁扩张**。
