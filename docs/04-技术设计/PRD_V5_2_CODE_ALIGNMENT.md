# 火瞳 PRD v5.2 与主分支代码对齐表

> 目的：为后续唯一融合 PRD 提供事实基线；本表不把“代码存在”表述为“门店验证通过”。
>
> 对照来源：WorkBuddy《火瞳_融合PRD_v5.2》、仓库 `docs/火锅AI-PRD-v5.0-融合版.md`、主分支代码。

## 1. 应采用的产品基线

- **产品定位**：冯校长火锅浙江总代的连锁 AI 运营中台；先椒江、玉环两家自营店验证，再形成区域标准。
- **产品边界**：视觉与数据双引擎；连接 POS/ERP，不替代正式收银、库存、采购或会员系统；采购与库存调整必须人工确认。
- **阶段门槛**：真实 POS 来源验收、真实回测、门店人工核验与访谈完成前，不得把数据引擎或 ROI 写为“已验证通过”。

仓库现有 v5.0 PRD 仍包含面向外部 SaaS 的客群、定价和扩张口径；它应被 v5.2 的“自有门店优先”战略覆盖，而不是并列为两套主方向。

## 3. 证据分层

1. **设计**：PRD、架构、路线图。
2. **代码**：模块可导入、接口/页面存在。
3. **模拟**：演示数据、Mock 传感器或生成 POS 数据。
4. **真实门店验证**：原始数据来源、人工核验、店长确认、前后对照。

只有第 4 层可以支持“已通过”“ROI 已验证”“区域标准已定版”等对外或运营结论。

## 4. 融合 PRD 的决策规则

- v5.2 的定位、两店路线、人工确认边界覆盖 v5.0 的旧外部 SaaS 口径。
- 功能状态统一为：`已具备代码基础`、`试点验证中`、`验证后开发`、`未来规划`；不再使用无证据的“已实现”。
- N01-N06 以 Sprint 0 为硬闸门；真实 POS 验收失败则降级为人工报表与人工订货建议。
- 所有分支的模块先映射到本表的功能编号和验收标准，只有补足缺口且无重复实现的代码才允许合入。
