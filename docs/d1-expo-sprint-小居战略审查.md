## 1. 战略一致性 — 评分 4/10 🔴

### 核心矛盾

经营哲学（`docs/火锅AI-经营哲学.md`，L20-21）明确宣告：

> 「我们只做一件事：边缘视觉AI看住火锅后厨。其他都是噪音。拿得少的人，反而赢。」

而 d1-expo-sprint 分支的 128 项功能已经远远超出"看后厨"的范畴，延伸到：

| 超出范围的功能类别 | 数量 | 经营哲学冲突 |
|-------------------|:---:|------|
| 前厅场景（K60-K69, K70-K72, FH01-FH02） | ~18项 | 经营哲学明确"不做C端流量、不做会员体系"（L18），但K61回头客识别、K62智能加菜、K67 6S服务评分等已侵入C端体验区 |
| 外部感知（N23-N25, K37） | 5项 | 对接美团/饿了么/抖音团购、竞品监控——这不是"看后厨"，这是在做市场情报平台 |
| 连锁管控（H01-H14） | 14项 | 总部云端平台/区域运营/加盟全生命周期——从2店验证跳到全国SaaS |
| 环境氛围（K68） | 1项 | 灯光/音乐/温湿度自动调控——这是智能楼宇，不是后厨视觉AI |
| 能耗管理（N27） | 1项 | 通用设施管理，与火锅后厨核心价值无关 |
| 卫生间管控（K70） | 1项 | 火锅后厨AI → 卫生间AI |
| 外卖打包（K71） | 1项 | 外卖平台聚合+骑手取餐管理——这是外卖SaaS |
| 自助调料台（K72） | 1项 | 蘸料区监控，边界模糊 |
| 设备维护工单（K73） | 1项 | 通用设备管理，非火锅特有 |

### 功能膨胀的量化证据

```
经营哲学定位：边缘视觉AI → 火锅后厨（单店）
PRD v5.3d 时的范围：63项，主要集中在后厨+前厅视觉+数据引擎
PRD v5.3i+ 范围：128项，覆盖全业态连锁经营

膨胀率：103% (63→128)，7小时内完成
与"克制"的距离：从"只做一件事"变成"做所有事"
```

### 克制宣言 vs 实际功能对照

| 经营哲学明确不做 | PRD 实际做法 | 冲突 |
|---------|------|:---:|
| 机器人/全自动厨房（L13） | 未做 | ✅ |
| 供应链全链路（L14） | S01-S04 冻品供应链 + N07-N09 供应商管理 | ⚠️ 边界模糊——"从蜀海/哗啦啦买，盒子只做品控" vs 实际做了货品主数据+验收+退换货+温控追溯+供应商画像+评级+对账 |
| 全球标准平台（L15） | H01-H14 连锁管控架构 | ⚠️ 虽然限定"先打中国市场"，但H01-H14已经是标准连锁SaaS平台的完整设计 |
| 云端大模型（L16） | 边缘推理，未做大模型 | ✅ |
| C端流量（L17） | K61回头客人脸识别、K62智能加菜推荐、N22菜品推荐 | 🔴 直接冲突——不做C端但做了客情识别+推荐 |
| 不做会员体系（L17） | N18会员消费数据分析 | ⚠️ 声明"不做会员CRUD和营销触达"但做"下游分析"，边界模糊 |

### 改进建议

1. **立即收敛产品边界**：展会前只保留经营哲学明确的范围——后厨视觉AI（K01-K05, K09-K12, K19-K22, K31, K38-K59）+ 数据引擎核心（N01-N06）+ 冻品供应链（S01-S03）+ 岗位助理（A01-A03）。其余约70+项标注为"Phase 2 远期愿景"。
2. **更新经营哲学**：如果确实要扩展到前厅和连锁管控，必须先更新经营哲学而非让它与PRD自相矛盾。当前经营哲学落后于PRD，是战略混乱的根源。
3. **建立"功能准入委员会"**：任何新增功能必须回答"这与'边缘视觉AI看火锅后厨'是什么关系？"——不能回答的不准入P0/P1。

### 风险等级：🔴 高
产品边界失控会导致：团队精力分散、展会Demo不聚焦、投资人困惑（"你们到底是做什么的？"）、资源浪费在非核心功能上。

## 2. 叙事完整性 — 评分 7/10 🟡

### 演进逻辑

v5.3d→v5.3i+ 的演进在PRD内部有清晰的因果链（深度理解文档 §5.2）：

```
v5.3d(63项·朴素功能清单)
  → v5.3e(场景工作流重构·哲学觉醒)
    → v5.3f(三大支柱设计哲学)
      → v5.3g(外部感知·双向数据流)
        → v5.3h(全场景人/物/料/环)
          → v5.3i(冷链全链路·加工区域全覆盖)
            → 3A-3F(经营闭环→连锁管控→多租户→Agent架构→技术架构)
```

**演进逻辑自洽**：从功能清单→场景工作流→设计哲学→架构系统性——这个演进方向是对的，每一步都有逻辑前提。

### 跳跃性

| 跳跃 | 跳跃幅度 | 问题 |
|------|:---:|------|
| v5.3i(单店94项) → 3B(连锁H01-H08) | **大** | 从2店验证直接跳到总部云端平台+区域运营+AI模型中心，中间缺少"3-5店标准化复制"的过渡态 |
| 3B(连锁管控) → 3D(多租户加盟) | **大** | 加盟连锁全生命周期管理、分账计费——这需要全国50+店才有实际需求 |
| K39 明火安全监测 | **中** | 火焰识别+燃气泄漏——跳到消防安全域，技术栈与视觉AI完全不同 |

### 单日极限迭代的叙事代价

36个commit在7小时内完成（深度理解文档 §8.1），平均12分钟一个commit。这保证了叙事的完整性和连贯性，但也导致：

- **缺乏外部反馈修正**：没有时间让PRD"沉淀"，所有决策在冲动下做出
- **越写越兴奋**：从"63项后厨AI"到"128项连锁帝国"，PRD撰写过程中的scope creep是肉眼可见的
- **CLAUD.md被抛弃**：CLAUDE.md仍标注"v5.3c，63项功能"，PRD已是v5.3i+ 128项——叙事与现实脱节

### 改进建议

1. **补写过渡态**：在3B与3D之间插入"3店标准化复制"阶段，验证从单店到多店的架构能否承载。
2. **同步CLAUDE.md**：这是最紧急的——所有AI工具都依赖CLAUDE.md了解项目状态，现在它是错的。
3. **标注版本边界**：明确"v5.3i单店能力"和"3A-3F远期愿景"的分界线，而不是混在一起让读者以为128项都要现在做。

### 风险等级：🟡 中
叙事本身完整，但跳跃导致外部读者（投资人、新团队成员）可能误判产品阶段。

## 3. 优先级合理性 — 评分 5/10 🔴

### P0/P1/P2 划分的内部一致性

PRD内部的优先级划分（深度理解文档 §3.2）逻辑上合理：
- P0（~34项）：展会Demo核心——后厨基础+数据引擎+冻品供应链+岗位助理+场景Agent
- P1（~30项）：展会后推进——会员/推荐/调拨/供应商协同
- P2（~55项）：12个月远期——连锁管控+多租户+Agent扩展

### 与展会时间窗的严重冲突

| 冲突 | 详情 |
|------|------|
| **P0的6项核心交付全部零代码** | S01-S03 + A01-A03 在D1-D2必须交付但一行代码没有（深度理解文档 §3.3） |
| **D1倒计时1周** | S01-S03（冻品供应链）必须在8月第1-2周完成，且依赖供应商王总外部配合（深度理解文档 §6.1） |
| **P0中H01-H08错误标注** | H01-H08 在功能统计表（PRD L684）中被标为P2，但在深度理解文档 §3.2 中被列为P0——优先级标记自相矛盾 |
| **SC01标P0但无代码** | 采购决策Agent是展会核心叙事的一部分，但目前只在PRD中有定义 |
| **KT01标P0但无代码** | 后厨数字孪生看板——展会Demo的核心展示项，同样是零代码 |

### P0功能分类（展会必须 vs 锦上添花）

| 类型 | 功能 | 展会必要性 |
|------|------|:---:|
| **必须跑通** | S01-S03冻品供应链、A01-A03岗位助理、K01-K05后厨+前厅视觉、N01-N06数据引擎核心 | 🔴 没有这些Demo就是PPT |
| **展示加分** | SC01采购决策Agent、KT01后厨数字孪生 | 🟡 有最好，但可以用视频Demo替代 |
| **展会后再说** | K60-K69前厅全场景、K70-K72外围、H01-H14连锁管控 | 🟢 展会上没人会问包间管控 |

### 改进建议

1. **重新定义P0为"展会必须跑的"**：砍到约15项核心功能（K01-K05 + K09-K12 + K19-K22 + K31 + N01-N06 + S01-S03 + A01-A03），其余标注"展会PPT展示（视频Demo）"。
2. **D1-D4冲刺聚焦6项**：S01-S03 + A01-A03，拒绝任何PRD新增功能直到D4完成。
3. **建立"优先级冻结"机制**：从今天起到展会结束，不再新增任何P0功能。

### 风险等级：🔴 高
如果按当前128项P0/P1/P2划分执行，团队会被优先级噪音淹没，展会Demo核心功能无法按时交付。

## 4. 差异化清晰度 — 评分 8/10 🟢

### 真正的护城河

这是d1-expo-sprint分支最强的维度。PRD的差异化定位（PRD L74-82）精准有力：

**真护城河（别人很难复制）：**

| 护城河 | 证据 | 壁垒深度 |
|--------|------|:---:|
| **双引擎闭环** | 视觉→数据→订货→损耗的完整闭环（PRD L77）。百度一见只做视觉巡检，ClearCOGS/PAR只做数据预测——没有人同时做视觉+数据并形成闭环 | 🟢 深 |
| **火锅垂直Knowhow** | 7工位SOP + 火锅周期因子 + 冻品供应链 + 食材级加工规则表（PRD §食材级加工管控规则表，L568-646）。泛化AI公司需要12-18个月才能积累同等深度的火锅行业知识 | 🟢 深 |
| **实地驱动设计** | 14张实拍照片→25项功能（深度理解文档 §5.3），椒江/玉环两店真实运营数据。这是任何纯技术公司无法在短时间内获得的真实现场洞察 | 🟢 深 |
| **人机协同哲学** | "数据是基础，AI是协助，人是决策"（PRD 3B.11章）——这不是功能，是产品哲学层面的差异化。与"AI替代人"的主流叙事形成鲜明对比 | 🟡 中 |

**"别人也能做"的功能（非护城河）：**

| 功能 | 为什么不是护城河 |
|------|------|
| K60-K69前厅全场景 | 等位排队、回头客识别、包间管理——这些都是成熟的餐饮SaaS功能，哗啦啦/客如云/美团都有 |
| K70卫生间管控 | 通用IoT，与火锅无关 |
| K71外卖打包 | 美团/饿了么商家版已有 |
| K72自助调料台 | 通用监控 |
| K68环境氛围调控 | 智能楼宇，不是火锅特有 |
| N27能耗管理 | 通用IoT，非差异化 |
| K73设备维护工单 | 通用工单系统 |

### 差异化的表达问题

虽然差异化定位清晰，但128项功能的"噪音"会稀释核心叙事。当投资人看到PRD目录时，从"后厨AI"到"卫生间管控"到"外卖打包区"到"设备维护工单"，他们会困惑："这到底是做什么的？"

### 改进建议

1. **展会叙事聚焦**：只讲"双引擎闭环+火锅垂直Knowhow"，砍掉所有非核心的故事线。
2. **标注护城河等级**：在PRD中为每项功能标注"护城河等级"（L1核心壁垒/L2行业标准/L3通用功能），让团队清楚哪些是必须在战场上守住的。
3. **竞品防御话术落地**：PRD已有竞品差异化定位表（L74-82），但缺少针对具体竞品（百度一见/喜虾客）的实战话术——展会Demo需要这个。

### 风险等级：🟢 低
差异化是火瞳最强的资产，但需要克制功能噪音来保护它。
