## 2. 数据状态标注与环境隔离规则

> **⚠️ 环境区分原则（v1.0 P0-5 强化）**：
> - **真实设备接入阶段**：摄像头/IoT传感器已物理部署，数据通过真实采集链路进入系统
> - **场景模拟验证阶段**：使用 Mock 数据验证算法管线，数据标记 `simulated`，**隔离于真实看板/展会数据**
> - **Pilot 称谓限定**：仅有真实事件已进入 Dashboard → Task → Agent → KPI 闭环的场景方可称为 pilot
> - **未接入状态**：硬件/接口未就绪的场景统一标注 `pending_integration`，不得简写为 `pending`
> - **Mock/模拟隔离规则**：`simulated` 数据仅存在于 dev/test/demo 环境，**严格隔离于真实展会数据流**，不得混入生产看板或 KPI 统计
>
> 每个场景标注其当前数据来源的真实性状态。状态定义遵循 PRD §1.11.6 的桩接口枚举体系：
> - `real` —— 真实设备/真实数据，已部署验证，可进入 Dashboard/Task/Agent/KPI 闭环
> - `simulated` —— Demo/Mock 模式，仅限 dev/test/demo 环境，隔离于真实数据流
> - `pending_integration` —— 已规划，硬件/接口待就绪，尚未接入真实设备

### 3.1 员工行为事件处理流程（⚠️ 合规约束）

> **核心原则**：AI 检测到的员工行为异常为 **疑似事件**，不作为绩效评估的自动输入或单一处罚依据。
> 所有疑似事件须经**人工复核→解释/申诉→管理者按制度决定**四步闭环方可作为管理参考。

#### 3.1.1 处理流程

```
疑似事件 (AI检测)
  ├─ K25/K43 行为检测事件 → agent_gateway.audit_log (event_type=BEHAVIOR_SUSPECT)
  ├─ 证据类型: 📸 抓拍照片 + 检测框标注 + 置信度分数
  ├─ ⚠️ 标注: "本事件为AI疑似判定，不作为单一处罚依据"
  ▼
人工复核 (L1 直接管理者)
  ├─ 后厨负责人(潘厨) 在 Edge UI 查看事件证据
  ├─ 复核枚举: ✅ 属实 / ⚠️ 存疑(需二次确认) / ❌ 误报 / 🔄 转上级裁决
  ├─ 复核时限: 事件推送后 60 分钟内完成或标记延期
  ├─ 证据查看权限: 仅本店管理者 + 当事人可查看自己的事件
  ├─ 证据保存期限: 疑似事件记录保存 90 天(自事件生成日起); 已确认属实的事件随绩效记录保存 2 年
  ▼
解释/申诉 (当事人)
  ├─ 入口: Edge UI "我的事件" → 查看疑似事件 → 提交解释/申诉
  ├─ 申诉渠道: ① Edge UI 在线申诉 ② 当面/电话向管理者口头说明(管理者录入系统)
  ├─ 申诉材料: 文字说明 + 可选附件(排班表/监控截图/证人陈述等)
  ├─ 在线申诉入口: Edge UI → 个人中心 → 我的疑似事件 → [申诉] 按钮
  ▼
管理者按制度决定 (L2 店长最终裁决)
  ├─ 店长综合复核结果 + 当事人解释/申诉 → 按门店管理制度作出决定
  ├─ 可选处理: 口头提醒 / 书面告诫 / 记入绩效参考 / 不予追究 / 误报关闭
  ├─ ⚠️ 强制约束: AI疑似事件不作为单一处罚依据，须结合人工调查+制度规定
  ├─ 决定记录: PG behavior_resolution 表 (event_id, reviewer, decision, basis, timestamp)
  └─ 闭环: 处理结果回写 audit_log，事件状态变更为 RESOLVED
```

#### 3.1.2 证据与权限矩阵

| 角色 | 查看权限 | 复核权限 | 申诉权限 | 裁决权限 |
|------|:--------:|:--------:|:--------:|:--------:|
| 当事员工 | ✅ 自己的事件 | ❌ | ✅ 提交申诉 | ❌ |
| 后厨负责人(潘厨) | ✅ 管辖区域内全部 | ✅ L1复核 | ❌ | ❌ |
| 店长 | ✅ 全店全部 | ✅ L2裁决 | ❌ | ✅ 最终决定 |
| 总部/总代 | ✅ 全店全部(只读) | ❌ | ❌ | ❌ |
| 系统管理员 | ✅ 全量(审计用途) | ❌ | ❌ | ❌ |

#### 3.1.3 数据保留策略

| 数据类型 | 保存期限 | 存储位置 | 过期处理 |
|----------|:--------:|----------|----------|
| 疑似事件原始记录 (含抓拍) | 90 天 | PG behavior_events + MinIO 图片存储 | 自动归档，图片删除 |
| 已确认属实的处理记录 | 2 年 | PG behavior_resolution | 到期归档至冷存储 |
| 误报/关闭事件 | 30 天 | PG behavior_events (status=CLOSED) | 自动清理 |
| 申诉材料 | 随关联事件保留 | MinIO behavior_appeals | 随事件同步过期 |

> **安全提示**：MinIO bucket 配置 lifecycle policy 自动执行过期清理，避免数据泄露风险。
> 任何员工行为数据的批量导出须经店长 + 总代双重审批。

## 4. Agent 订阅确认复核矩阵

> 配置遵循 PRD §1.11.5 的四维最小字段集（权限/订阅/推送/审批）。

| Agent | 岗位角色 | 订阅事件 | 谁确认 (Confirm) | 谁复核 (Review) | 复核频率 | 超时未处理升级至 |
|-------|----------|----------|:----------------:|:---------------:|:--------:|----------------|
| **A01 店长助理** | 店长 | K01/K02 废料日报、K05 空桌超时、K13 翻台率、N02 采购建议、S02 收货异常、K19 温度告警 | 店长本人 | — | 每日 | —（最终决策者） |
| **A02 后厨助理** | 后厨负责人(潘厨) | K01/K02 废料事件(实时)、K27 SOP违规、K31 出品异常、K19 温度告警、K25 行为异常 | 潘厨本人 | 店长(A01) | 每日 | 店长(A01) |
| **A03 采购助理** | 采购员 | N02 采购建议、N03 库存预警、N04 损耗报告、S02 收货任务 | 采购员本人 | 店长(A01) | 每次采购周期 | 店长(A01) |
| **A04 供应商协同端** | 供应商联系人 | S02 收货验收通知、S03 退换货通知、N08 评级更新 | 供应商方确认 | 采购员(A03) | 每次交互 | 店长(A01) |
| **A05 知识库助理** | 全员共享 | SOP查询、菜品知识、设备操作指南（被动查询，非主动推送） | 查询者本人 | — | 按需 | — |

> **确认语义**：
> - **确认 (Confirm)**：对 AI 生成的事件/建议进行人工确认，确认后事件进入"已处理"状态
> - **复核 (Review)**：上级角色对下级的确认结果进行二次审核，确保处理质量
> - **超时升级**：确认者未在规定时间内响应，系统自动向上级发出升级通知

> **椒江店 Agent 实例化约束**：
> - A02(后厨助理) 只能查看 `zone_kitchen` + `zone_cold_storage` 的数据，不能查看前厅数据
> - A03(采购助理) 不能直接创建正式采购订单（需店长审批），只能生成采购建议
> - 所有 Agent 的操作记录写入 `agent_gateway.audit_log`，携带 tenant_id/store_id/agent_id/timestamp 完整上下文

## 5. 验收证据链：事件→任务→推送→人工处理→KPI

> **验收方法论**：每个业务场景必须形成完整的证据链——从 AI 检测事件，到生成待办任务，到推送给责任人，到人工确认处理，到最终体现为 KPI 改善。
> **证据类型**：
> - 📸 截图/录屏 —— Edge UI 界面截图
> - 📊 数据记录 —— PostgreSQL 审计日志
> - 📝 人工签字/确认 —— 微信/Edge UI 操作记录
> - 📈 KPI 变化 —— 前后对比数据

### 5.1 后厨废料检测验收链

```
事件 (Event)
  ├─ K01 废料检测事件 → agent_gateway.audit_log (event_type=WASTE_DETECTED)
  ├─ 证据: 📸 Ch101 抓拍照片 + YOLO 检测框标注截图
  ▼
任务 (Task)
  ├─ 系统自动生成待办任务: "处理废料事件 #W2026-08-07-001"
  ├─ 证据: 📊 PG task 表记录 (task_id, status=pending, assignee=潘厨)
  ▼
推送 (Push)
  ├─ Edge UI 实时推送 + 声音提示
  ├─ 证据: 📸 Edge UI 推送界面截图 + PG notification_log 表记录
  ▼
人工处理 (Human Action)
  ├─ 潘厨在 Edge UI 点击"确认处理" → 填写原因(选填) → 拍照上传
  ├─ 证据: 📊 PG audit_log (action=CONFIRM, operator=潘厨, timestamp)
  ▼
KPI 闭环 (KPI Evidence)
  ├─ 指标: 废料处理及时率 = (3min内处理数 / 总废料事件数) × 100%
  ├─ 指标: 日废料金额变化趋势（介入前 vs 介入后对比）
  ├─ 证据: 📈 N04 损耗分析报告（周报/月报）
```

### 5.2 采购建议验收链

```
事件 (Event)
  ├─ N01 销量预测完成 (凌晨 01:30 批处理) → N02 生成采购建议
  ├─ 证据: 📊 PG sales_forecast 表 + order_suggestion 表
  ▼
任务 (Task)
  ├─ 系统生成: "今日采购建议: 毛肚 15kg / 鸭肠 8kg / ..."
  ├─ 证据: 📊 PG task 表记录 (task_type=PURCHASE_REVIEW)
  ▼
推送 (Push)
  ├─ Edge UI + 微信模板消息 (早 08:00)
  ├─ 证据: 📸 微信推送截图 + PG notification_log
  ▼
人工处理 (Human Action)
  ├─ 店长查看建议 → 调整数量 → 确认生成采购单 (S03)
  ├─ 采购员在 Edge UI 点击"确认下单" → 审批流通过
  ├─ 证据: 📊 PG purchase_orders 表 + audit_log (approval chain)
  ▼
KPI 闭环 (KPI Evidence)
  ├─ 指标: 采购建议采纳率 = (采纳项数 / 建议项数) × 100%（目标 ≥ 60%）
  ├─ 指标: 库存周转天数（介入前 vs 介入后对比）
  ├─ 证据: 📈 N01 预测准确率对比 (MAPE) + N03 库存快照
```
