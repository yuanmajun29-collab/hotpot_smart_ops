## 第一章 总体目标

### 1.1 背景

火瞳系统当前存在以下"单店/Demo/固定配置"倾向：

1. **文档和代码中直接引用椒江店名、IP、摄像机ID作为默认事实**
2. **API/事件/任务缺少租户和门店上下文字段**
3. **Agent 按单店角色写死，无法复用到其他门店**
4. **Demo 数据和真实数据未严格隔离**
5. **端口、路径、环境变量命名不统一**

### 1.2 改造目标

将系统从 **"单店、Demo、固定配置"** 收敛为 **"多租户、多门店、云边协同、配置驱动"** 的连锁餐饮 AI 智能体运营平台。

### 1.3 核心约束

- 椒江店可作为**真实样板店、开发默认实例和展会验证对象**
- 但**不得写入系统逻辑、权限判断、设备路由或业务规则**
- 所有门店数据均为对象模型的**实例数据**，非系统默认值

## 第二章 统一对象模型

### 2.1 十二层对象层级

```
租户 Tenant → 品牌 Brand → 区域 Region → 门店 Store → 边缘盒子 Edge Device
    → 摄像机/IoT Device → 业务区域 Zone → 场景 Scene
    → 模型策略 Model Profile → 规则策略 Rule Profile → 岗位 Agent
```

### 2.2 层级定义表

| 层级 | 标识符 | 说明 | 示例 |
|------|--------|------|------|
| 租户 | `tenant_id` | 独立经营主体（自营/加盟） | 浙江总代（自营）、加盟商A |
| 品牌 | `brand_id` | 租户下的品牌线 | 冯校长火锅 |
| 区域 | `region_id` | 品牌下的地理区域 | 台州区、玉环区 |
| 门店 | `store_id` | 具体运营门店 | 椒江店(store_001)、玉环店(store_002) |
| 边缘盒子 | `edge_device_id` | 部署在门店的边缘计算设备 | jetson_jiaojiang_001 |
| 摄像机/IoT | `source_device_id`（类型为 camera/sensor/scale 等） | 南向感知设备 | ch101(主厅俯拍)、ch102 |
| 业务区域 | `zone_id` | 门店内的业务分区 | zone_kitchen(后厨)、zone_hall(前厅) |
| 场景 | `scene_id` | 区域内的具体业务场景 | scene_waste_detect(废料检测) |
| 模型策略 | `model_profile_id` | 场景绑定的AI模型+参数配置 | yolo_waste_v2 + clip_sop_v1 |
| 规则策略 | `rule_profile_id` | 场景绑定的业务规则+阈值 | waste_threshold_medium |
| 岗位Agent | `agent_id` | 绑定到角色+组织范围的AI助理 | agent_store_manager(店长助理) |

### 2.3 层级关系规则

- 一个租户可拥有多个品牌、区域和门店；门店可拥有多个边缘盒子和南向设备
- 摄像机按仓库、后厨、前厅、入口、收银、包间等区域绑定；ROI、算法、抽帧频率和告警规则均可配置
- **椒江店只是该对象模型中的一组真实实例数据，不是系统默认业务模型**

## 第三章 多租户与多门店

### 3.1 默认门店规范

- 允许在开发环境和页面首次加载时设置 `default_store_id`（如椒江店 store_001）
- 默认门店**仅用于**初始化、空状态引导和开发调试
- 登录后必须依据租户、区域、门店、岗位权限确定数据范围
- 总部可查看授权多店，区域管理者查看授权区域，店长和一线员工默认本店与本岗位
- 所有 API、事件、任务和 Agent 请求**必须显式携带**并由服务端校验上下文
- **默认值不得参与权限判断、设备路由、数据库关联或业务规则**

### 3.2 权限层级

| 角色 | 数据范围 | 操作权限 |
|------|----------|----------|
| 老板/总代 | 全租户所有门店 | 只读+审批 |
| 区域运营 | 授权区域内多店 | 读写+审批 |
| 店长 | 本店全数据 | 读写+确认 |
| 一线岗位 | 本店本岗位数据 | 读写+确认 |

## 第四章 配置中心

### 4.1 配置分层

| 层级 | 存储方式 | 示例 | 禁止事项 |
|------|----------|------|----------|
| 租户/门店基础信息 | 云端DB `tenants` / `stores` 表 | 名称、地址、联系人 | ❌ 硬编码门店名/IP |
| 设备凭证 | 密钥管理服务 / 环境变量 | `{NVR_PASSWORD}`、`{EDGE_TOKEN}` | ❌ 明文密码写入代码/文档/Git |
| API端点/端口 | 配置文件 + 环境变量 | `EVENT_HUB_PORT=8098` | ❌ 端口硬编码 |
| 模型参数 | 云端配置 `model_profiles` 表 | ROI坐标、置信度阈值 | ❌ 单店模型参数写死 |
| 业务规则 | 云端配置 `rule_profiles` 表 | 告警阈值、升级超时 | ❌ 规则硬编码 |

### 4.2 红线

> ⚠️ **禁止将真实 IP、摄像机账号、密码、API Key 写入代码、Git 配置或文档示例。统一使用环境变量、凭证引用和密钥管理。**

## 第五章 云边通信契约

### 5.1 协议统一

北向注册、心跳、配置拉取、事件上报、离线补传统一为一套版本化协议，并统一使用 `/api/v1` 前缀。

### 5.2 业务事件必携字段（16项 = 9通用 + 3感知来源 + 4视觉扩展）

> **注**：PRD §1.11.4 定义了统一的三层事件字段结构。`source_device_id` 统一表示来源设备（类型为 camera/sensor/scale 等），不再单独使用 `camera_id`。

**第一层：通用必填（9字段，所有事件/任务/KPI 必须携带）**

| # | 字段 | 类型 | 说明 |
|---|------|------|------|
| 1 | `tenant_id` | string | 租户标识 |
| 2 | `brand_id` | string | 品牌标识 |
| 3 | `region_id` | string | 区域标识 |
| 4 | `store_id` | string | 门店标识 |
| 5 | `event_id` | string | 事件唯一ID（UUID） |
| 6 | `correlation_id` | string | 关联事件ID（事件链追踪） |
| 7 | `event_type` | string | 事件类型枚举 |
| 8 | `occurred_at` | datetime | 事件发生时间（ISO 8601） |
| 9 | `source_status` | string | 数据源状态（real/simulated/stub/pending） |

**第二层：感知来源必填（3字段，边缘/设备上报事件携带）**

| # | 字段 | 类型 | 说明 |
|---|------|------|------|
| 10 | `edge_device_id` | string | 边缘盒子标识 |
| 11 | `zone_id` | string | 业务区域标识 |
| 12 | `source_device_id` | string | 来源设备标识（摄像机/传感器/电子秤等） |

**第三层：视觉/模型扩展（4字段，仅视觉推理事件携带）**

| # | 字段 | 类型 | 说明 |
|---|------|------|------|
| 13 | `model_name` | string | 产生此事件的AI模型名 |
| 14 | `model_version` | string | 模型版本号 |
| 15 | `confidence` | float | 模型置信度 (0~1) |
| 16 | `evidence_ref` | string | 证据文件引用路径 |

### 5.3 通信保障

- 设备采用可轮换凭证和首次注册令牌
- 配置采用版本号 + ACK + 失败回滚 + 审计
- 事件上报支持**幂等**（event_id去重）、**重试**（指数退避）、**死信队列**（超时未处理）与**断网补传**（离线队列）
- **云端是事件、任务、审计和 KPI 的主写入端；边缘仅保留缓存、必要证据与离线队列**

## 第六章 Agent 配置化

### 6.1 五维配置模型

> **核心原则**：岗位 Agent **不得按单店或单个页面写死**。每个 Agent 均通过以下 5 维配置驱动：

| 配置维度 | 说明 | 示例 |
|----------|------|------|
| 角色 `role` | Agent绑定的岗位角色 | store_manager(店长)/kitchen_head(后厨负责人)/purchaser(采购) |
| 组织范围 `org_scope` | 可访问的租户/区域/门店集合 | `{"tenant_id": "t_001", "store_ids": ["store_001", "store_002"]}` |
| 数据范围 `data_scope` | 可查看的数据类型与粒度 | 店长看全店数据，厨师只看后厨数据 |
| 订阅策略 `subscription` | 关注的事件类型+阈值+频率+渠道 | 见 PRD §1.10.2 |
| 动作策略 `action_policy` | 允许执行的操作+需审批的操作 | 建议/推送/创建待办（✅）；自动下单/扣库存（❌需审批） |

### 6.2 审计要求

Agent 的查询、建议、推送、工具调用和人工处理结果均应携带完整上下文（tenant_id/store_id/agent_id/timestamp）并记录至 `agent_gateway.audit_log`。

### 6.3 红线

员工行为相关能力（如SOP违规检测）只可生成"**疑似事件**"，**不得基于视觉结论自动处罚**。处罚决定必须由人工确认。（符合《最终方案》第六章、PRD §1.7 RL-2）

## 第七章 Demo/Mock 隔离

### 7.1 五级环境分类

| 环境 | Demo/Mock允许 | 数据隔离要求 |
|------:|:---:|------|
| 开发环境 `dev` | ✅ 允许Demo图片、随机数据、模拟KPI | 与真实数据物理分离 |
| 测试环境 `test` | ✅ 允许Mock模型、模拟POS | 必须标记 `source_status=simulated` |
| 演示环境 `demo` | ✅ 仅用于展会/演示 | 独立demo profile，不混入真实事件流 |
| 试点环境 `pilot`（椒江店） | ❌ **禁止**Mock进入真实事件/看板/报表 | 真实数据唯一来源 |
| 生产环境 `prod` | ❌ **严格禁止** | 违反即视为P0安全事件 |

### 7.2 桩接口返回码约定

| 返回值 | 含义 | 使用场景 |
|--------|------|----------|
| `not_connected` | 设备未接入 | IoT传感器等尚未部署的能力 |
| `disabled` | 功能已禁用 | 租户未购买的功能模块 |
| `simulated` | 模拟数据 | 仅限dev/test/demo环境 |
| `pending_integration` | 待集成 | 已规划但尚未对接的外部系统 |

### 7.3 成熟度表述规范

| 标识 | 含义 | 判定标准 |
|------|------|----------|
| 📋 L1 | 需求/设计文档已完成 | PRD/架构有明确定义 |
| 🔧 L2 | 有可运行代码/Demo | 可演示，但非真实门店验证 |
| ✅ L3 | 真实门店连续运行≥7天+KPI回写+业务闭环 | 三条件同时满足 |
| ⭐ L4 | 生产可用（多店复用+ROI） | ≥2家门店稳定运行 |

## 第九章 验收标准

| # | 验收项 | 通过标准 |
|---|--------|----------|
| A-1 | 新门店零代码接入 | 新增门店只录入组织、设备、区域、规则和人员权限，**不修改业务代码** |
| A-2 | 门店切换一致性 | 椒江店可作为默认开发/展会样板，但切换其他门店后**系统逻辑保持一致** |
| A-3 | 数据严格隔离 | 真实数据(`source_status=real`)、桩数据(`stub`)、Demo数据(`simulated`)在配置、接口、看板、Agent和审计层**严格隔离** |
| A-4 | 全量上下文携带 | 所有用户、设备、事件、任务、Agent与审计记录**均具有租户和门店上下文**（tenant_id/store_id） |
| A-5 | Agent配置化运行 | 每个岗位Agent支持权限内订阅、主动推送、查询、指导、人工确认和闭环追踪 |
| A-6 | 文档表述一致性 | 系统文档、接口、配置、部署脚本对门店、端口、路径、环境及成熟度的**表述完全一致** |

## 第十章 补充整改项（复评发现）

> **来源**：2026-08-06 对 `feature/arch-design` 分支文档的二次复评

### P0-A：通用化方案链接指向仓库外部

**问题**：PRD 上游输入行和 §1.11 来源行均使用相对路径指向仓库外部的 `.docx` 文件：
```
[`系统设置与架构通用化修改方案`](../../../火瞳_系统设置与架构通用化修改方案.docx)
```

**影响**：
- Git 仓库内无法追溯该文档内容
- 其他协作者无法访问该外部文件
- CI/CD 链接检查会报 broken link

**修复方案**：将通用化方案转化为 Markdown 纳入仓库（即本文档），PRD 链接改为内部引用。

### P0-B：PRD 中部分功能标记"已完成"但实际未实现

**问题**：功能清单中部分条目的"当前状态"列可能标记为比实际更高的成熟度级别。

**修复方案**：建立「目标设计 vs 当前实现 vs 验收证据 vs 责任人」对照表，逐项核实。

### P1-A：版本号不一致

**问题**：多个文档间版本号引用存在偏差（如 v5.3n/v5.3o 混用、v1.5/v1.6 混用）。

**修复方案**：以 PRD 为权威源头，统一全部下游文档的版本引用。

### P1-B：事件 schema 字段数量表述不一致

**问题**：§1.11.4 正文写"14项"但表格实际列出 16 个字段。

**修复方案**：明确分类——14 项通用必填 + 2 项扩展字段（evidence_ref, source_status），或统一修正为 16 项。

### P1-C：详细架构中使用硬编码店名作为泛化示例

**问题**：详细架构设计的某些示例中仍使用"椒江店""玉环店"作为通用示例名称。

**修复方案**：泛化示例中使用 `tenant_demo` / `store_demo` / `store_pilot` 等占位符。
