# 火瞳餐饮 AI 智能体运营系统整改方案

> **文档性质**: 权威基准 · 架构整改纲领
> **版本**: v1.0
> **日期**: 2026-08-04
> **来源**: 项目方整改要求
> **状态**: 已批准，待执行

---

## 一、整改目标

火瞳定位为面向连锁餐饮的 AI 智能体运营系统，而非传统 ERP。整改目标是建立"边缘实时感知、云端统一治理、岗位智能体协同、人机确认执行"的单一闭环，最终实现：

1. 降本增效；
2. 提高出品率；
3. 管控人员并提升人效；
4. 提高前厅服务效率与质量；
5. 实现供应链、食品安全、人/物/料/环的可追溯管理。

## 二、当前核心问题

1. Edge UI、本地 JSON/PIN 与云端 Hub/JWT/PG 并存，主数据、权限、审计和业务流程双轨。
2. 边缘 Web、摄像头、IoT、模型、北向协议、部署脚本存在多套入口与配置漂移。
3. 后厨 VLM、前厅待清台、采购收货等有代码和演示基础，但真实门店端到端闭环证据不足。
4. 收货 VLM 仍是 Mock；多区域设备覆盖、加盟治理、自然语言 Agent、主动推送和 CI 尚未形成生产能力。
5. 员工行为管理只有通用识别与告警基础，尚未形成合规的岗位离岗、报备、人工复核和申诉流程。

## 三、目标架构

```
门店边缘设备(摄像头/IoT/POS)
    ↓
边缘感知与计算(抽帧/AI/VLM/离线缓存)
    ↓
云端 Hub(统一事件/主数据/权限/审计)
    ↓
业务平台(损耗/库存/采购/收货/任务/审批)
    ↓
岗位 AI 智能体(总部/区域/店长/后厨/采购/前厅)
    ↓
人工确认与执行
    ↓ (回流)
云端 Hub
```

**边缘侧**保存：实时原始感知、高频 IoT 数据、即时推理结果、断网队列
**云端保存**：结构化事件、关键证据引用、经营数据、任务、审批、审计、跨店汇总

**所有事件必须携带**：门店、设备、区域、时间、关联编号、模型版本、置信度。

## 四、P0：统一底座

### 1. 统一主 Hub

将 D1-D3 的货品、采购、收货、供应商、岗位建议、审批和审计全部迁入 Hub 的正式数据库与 API。

- Edge UI 仅作为本地配置与业务客户端，不再承担生产主数据主写。
- 统一使用 JWT、RBAC、门店/区域/租户隔离和 PG 审计。
- 建立门店、设备、员工、菜品、原料、供应商、批次、订单和事件的统一 ID。
- 所有跨服务流程使用同一关联编号。

### 2. 统一边缘南北向协议

- Edge Web 成为唯一的门店配置中心：网络、摄像头、IoT、Hub、模型、岗位订阅、规则阈值统一管理。
- 北向仅保留一套设备注册、心跳、配置拉取、事件上传、命令回执与离线重传协议。
- 增加设备身份签名、配置版本、确认回执、幂等、断点续传和健康检查。
- 清理旧端口、旧启动脚本、Mock 默认回退和明文凭证。

### 3. 建立统一事件与审计模型

每个 AI、IoT 或业务事件都统一记录：

- 门店、区域、设备、摄像头/传感器；
- 时间、区域、人/物/料/环对象；
- 原始证据引用、模型与规则版本、置信度；
- 告警、任务、审批、处理结果；
- 推送、阅读、确认、忽略、操作与审计记录。

## 五、P1：优先完成四条真实闭环

### 1. 后厨损耗与出品率闭环

收货批次 → 备料 → SOP/出品抽检 → 废料识别与称重 → 原因确认 → 店长复核 → 采购/备货建议 → 成本结果。

先选 1–2 个高频菜，验证一次合格率、份量偏差、返工/退菜率、废料占比和单位原料出品份数。

### 2. 预测、库存与采购闭环

POS/销量/库存/天气/节假日 → 预测 → 采购建议 → 人工审批 → ERP 待办或人工下单 → 收货 → 消耗与偏差回灌。

AI 只能生成建议和待办；正式采购必须由授权人员确认。

### 3. 冻品收货与供应商闭环

采购订单 → 品牌/规格/温度/重量/影像 → 真实 VLM 辅助质检 → 授权人员签字 → 入库、拒收或退换 → 批次追溯 → 供应商评分。

收货 VLM 必须从 Mock 接入真实 Bridge，但 VLM 仅辅助判断，不替代人工食安与收货责任。

### 4. 前厅待清台与服务闭环

入口客流/桌台状态 → 待清台事件 → 前厅领班/服务员任务 → 接单、完成、纠正 → 超时升级店长 → 翻台与服务响应复盘。

先完成 6–10 张桌、一家门店、连续 7 天验证；再扩展入口、收银、包间、加汤和主动服务。

## 六、P1：岗位 AI 智能体整改

建立唯一 Agent Gateway，统一处理身份、租户、门店、岗位、数据范围、工具白名单、审批和审计。

第一批上线店长、后厨、采购、前厅领班四类 Agent，每个都具备：

1. 主动推送岗位异常、待办和机会；
2. 自然语言查询权限范围内的数据和 SOP；
3. 解释发生原因、经营影响和建议；
4. 创建任务、发起审批、跟踪结果；
5. 高风险动作必须人工确认。

订阅控制"岗位希望接收什么信息"，RBAC 控制"岗位允许查看和操作什么"，两者独立管理。

## 七、员工行为管理整改边界

员工行为功能只能用于安全、流程与运营改进，不能以视觉识别直接自动处罚。

如新增晚高峰疑似离岗能力，应遵循：

- 定义员工岗位、班次、责任区域和已批准报备；
- 系统只识别"离开责任区"，没有可靠证据时不得推断"上厕所"；
- 在可配置高峰时段内，连续超过阈值仅生成"疑似离岗事件"；
- 店长或 HR 必须先核对报备并人工复核；
- 员工可查看、解释和申诉；
- 视觉结论不得自动扣薪、处分或影响排班；
- 截图最小化、加密、限期保留，查看和下载全程审计；
- 上线前完成劳动与个人信息保护合规审查、员工告知和真实误报验证。

## 八、P2：加盟治理与生产交付

- 建立 tenant、brand、region、store、device、user、role、policy 的正式模型。
- 明确直营与加盟的数据边界、品牌策略继承、设备生命周期和门店上线流程。
- 固化新店标准包：设备清单、点位模板、网络要求、数据接入、岗位配置、SOP、培训、验收和运维。
- 固定唯一启动入口、镜像、模型、端口、密钥管理、备份恢复和健康检查。
- 建立 CI：静态检查、单元测试、接口测试、离线重传、硬件模拟与端到端冒烟测试。

## 九、验收闸门

### 技术闸门

设备稳定、数据完整、协议统一、权限正确、审计可追溯、部署可复现、CI 可验证。

### 产品闸门

岗位人员持续使用；主动推送少而准；自然语言回答有依据；任务、审批和复核真正形成闭环。

### 业务闸门

以门店前后对照验证：

- 损耗率、报废额、采购价差、库存周转；
- 一次合格率、份量偏差、返工/退菜率；
- 人均订单/工时、任务按时率、告警响应时长；
- 迎宾、点单、上菜等待时间、翻台率、投诉与满意度。

## 十、实施顺序

1. **统一 Hub、身份、事件、审计、边缘北向协议和部署方式。**
2. **做一店后厨损耗、冻品收货、前厅待清台三条真实闭环。**
3. **将店长、后厨、采购、前厅领班 Agent 接入统一 Gateway。**
4. **用真实数据完成两店经营指标前后对照。**
5. **再扩展区域/总部 Agent、加盟治理、多区域点位与外部复制。**

---

> 最终目标不是堆叠视觉模型、页面或 Agent 数量，而是形成一套可持续的连锁餐饮经营操作系统：现场自动感知，数据统一治理，AI 按权限辅助岗位，关键动作人工确认，经营结果持续回流优化。
