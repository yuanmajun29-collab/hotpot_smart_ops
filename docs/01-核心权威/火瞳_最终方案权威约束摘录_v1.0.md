## 一、产品定位（摘录自《最终方案》第二章）

### 1.1 产品是什么

| 维度 | 定义 |
|------|------|
| **是什么** | 面向连锁餐饮的 **AI 智能体运营系统** |
| **不是什么** | 传统 ERP 替代品、纯视觉巡检系统、纯数据 BI 工具 |
| **核心价值** | 把门店现场事实转成：可处理的事件、可解释的建议、可追踪的任务、**可验证的经营改善** |

### 1.2 火瞳与其他系统的关系

- 火瞳 **连接** POS、ERP、库存、采购和会员系统，**不取代**它们
- 火瞳可给出预警、损耗估算和订货建议；正式采购、库存扣减和关键食安处置必须由授权人员确认
- 火瞳是运营中台的"大脑"和"眼睛"，不是业务系统的替代品

## 二、云边协同原则（摘录自《最终方案》第三章）

### 2.1 边缘+云端双层架构

| 层级 | 定位 | 核心能力 |
|------|------|----------|
| **边缘端（Jetson 盒子）** | 实时感知与本地推理 | YOLO 视觉检测、摄像头抓拍、IoT 数据采集、本地事件生成 |
| **云端（Hub + Dashboard）** | 数据聚合与智能决策 | 数据引擎（预测/订货/损耗/库存）、多店对比、Agent 调度、Dashboard 展示 |

### 2.2 数据流向规则

1. **实时数据边缘处理**：摄像头视频流在 Jetson 边缘完成推理，不上传原始视频
2. **结构化事件上云**：边缘仅上传结构化事件（事件类型、时间戳、置信度、证据引用），不含原始图像
3. **云端决策下发**：预测结果、订货建议、SOP 更新从云端下发到边缘
4. **离线降级**：网络中断时边缘独立运行，恢复后自动同步

### 2.3 数据治理原则

1. **最小化采集**：只采集与经营改善直接相关的数据字段
2. **分层可见**：店长看单店经营数据、区域经理看多店对比、老板看 ROI 总览
3. **原始数据不出门店**：视频流、原始 POS 导出始终存储在门店本地/边缘，云端仅保留结构化事件和聚合指标
4. **数据归属明确**：门店经营数据归属门店/品牌所有，火瞳仅作为数据处理方

## 三、Agent 权限与行动边界（摘录自《最终方案》第七章 表格35）

### 3.1 岗位 Agent 行动边界（红线）

| Agent | 第一阶段职责 | **行动边界（绝对红线）** |
|-------|------------|----------------------|
| **店长 Agent (A01)** | 今日异常、经营复盘、任务优先级、跨岗位协调 | 可创建/跟进任务；**关键经营动作需授权确认** |
| **后厨 Agent (A02)** | 备货、SOP、损耗、温控、出品风险指导 | 可提示与生成整改任务；**不直接扣减库存** |
| **采购 Agent (A03)** | 预测、库存风险、比价、订货建议、到货跟踪 | 可生成建议和待办；**正式下单必须审批** |
| **收货/质检 Agent (S02)** | 来货核验、VLM 辅助质检、异常与复核 | 可建议通过/驳回；**最终签字由授权人员完成** |

### 3.2 Agent 权限五维模型（摘录+火瞳 PRD 扩充）

> 以下五维模型是本摘录基于《最终方案》第七章 Agent 行动边界 + PRD §1.11.5 设计扩展而成，用于指导火瞳代码实现。

| 维度 | 含义 | 示例值 |
|------|------|--------|
| `can_query` | 可查询哪些数据域 | `["waste", "inventory", "sales", "sop"]` |
| `can_advise` | 可生成哪类建议 | `["reorder", "task_assign", "waste_reduce"]` |
| `can_push` | 可通过哪些渠道推送 | `["wechat", "dashboard", "sms"]` |
| `can_create_todo` | 可创建待办任务 | `true` (店长/后厨) / `false` (供应商) |
| `can_approve` | 可审批哪类动作 | `["waste_confirm"]` (店长) / `[]` (后厨) |

## 四、订阅与推送机制（摘录自《最终方案》第七章）

### 4.1 推送权限

- 系统可主动推送告警、异常、待办提醒
- 推送目标按角色和权限过滤：店长收经营类告警、后厨收损耗/SOP 告警、采购收库存/订货提醒
- 每个 Agent 实例的推送渠道（微信/短信/Dashboard）、推送频率、静默时段由配置管理

### 4.2 订阅规则

- 每个角色按事件类型订阅（如：后厨订阅 K01 废料检测 + K10 SOP 违规事件）
- 支持阈值过滤（如：仅在损耗金额 > ¥50 时推送）
- 支持时间窗口（如：只在 06:00-22:00 推送）

## 五、人工确认与审批链（摘录自《最终方案》第六章）

### 5.1 核心原则

> **AI 不自动创建正式采购订单，不自动扣减库存，不自动执行关键食安处置。**
>
> 所有涉及资金、库存、食安的正式操作必须经过授权人员人工确认。

### 5.2 审批链设计

| 动作类型 | 审批人 | 审批方式 | 超时机制 |
|----------|--------|----------|----------|
| 采购订单创建 | 店长（或授权采购人员） | Dashboard/手机确认 | 48h 超时自动提醒+升级到区域经理 |
| 库存扣减确认 | 后厨主管/店长 | 手机确认 | 当日关店前处理 |
| 废料原因确认 | 后厨人员 | 手机选择原因分类 | 2h 内完成，超时默认记入"未分类损耗" |
| 供应商退换货 | 店长 + 采购 Agent 协同 | 审批流 | 72h 内闭环 |

## 六、员工行为不自动处罚（摘录自《最终方案》第八章）

### 6.1 绝对红线

> **火瞳系统不得对员工行为实施自动处罚。**
>
> 包括但不限于：自动扣款、自动降级、自动辞退建议、自动绩效扣分。
>
> AI 的角色是**辅助发现和提醒**，不是**替代管理者做人事决策**。

### 6.2 正确做法

| 场景 | AI 可以做什么 | AI 不能做什么 |
|------|-------------|--------------|
| SOP 违规检测 | 记录违规事件、推送提醒给店长 | 自动扣绩效分、自动生成处罚单 |
| 损耗异常 | 检测废料量、分析损耗趋势 | 自动追究责任人、自动扣工资 |
| 出勤异常 | 记录到岗/离岗时间 | 自动判定迟到/早退并处罚 |
| 员工行为识别 | 识别行为模式、推送异常提醒 | 自动生成员工评估报告、自动标记"问题员工" |

### 6.3 数据留存规则

- 员工行为相关数据保留用于经营分析，但不得作为单一证据用于处罚
- 处罚决定必须结合人工复核、多方证据、员工申诉后方可执行
- 员工行为数据的访问权限限定于店长及以上角色

## 七、样板店与通用平台边界（摘录自《最终方案》第四章）

### 7.1 样板店定位

| 属性 | 椒江样板店 | 通用平台 |
|------|----------|----------|
| **角色** | 真实经营验证 + 流程打磨 | 标准化部署 + 多店复制 |
| **数据** | 原始 POS/库存/摄像头数据 | 标准化数据模型 + 配置模板 |
| **配置** | 允许硬编码/手动调优 | 配置驱动，禁止单店硬编码 |
| **验证标准** | 连续运行 7 天 + KPI 达标 | 新店部署 < 1 天 + 零配置启动 |

### 7.2 通用化基线要求

> 系统软件层必须做到：**在样板店验证通过的功能，可通过配置（非代码修改）部署到新门店。**
>
> 椒江店只是对象模型的第一个实例，不是系统的唯一逻辑。

### 7.3 样板店→通用平台的过渡路径

```
当前阶段（两店验证）：
  椒江店（首座样板店） + 玉环店（第二验证店）
  ↓ 允许部分硬编码，重点跑通业务闭环

目标阶段（展会后）：
  配置驱动的通用平台
  ↓ 新店部署通过 Dashboard 添加门店 → 配置下发 → 自动接入
```
